# Требования к OrderFlow

## 1. Цель
Обеспечить предсказуемое оформление и отмену заказов с согласованным состоянием заказа и складских остатков.

## 2. Пользователи и заинтересованные стороны
- Покупатель: хочет быстро оформить заказ и видеть понятный результат.
- Владелец магазина: хочет избежать заказов сверх доступного остатка.
- Команда разработки: нуждается в однозначных правилах и контрактах.
- QA: нуждается в проверяемых требованиях и ожидаемых результатах.

## 3. Допущения
- Валюта одна для всего магазина в рамках MVP.
- Оплата и доставка не реализуются.
- Заказ в MVP содержит одну или несколько позиций.
- Остаток товара хранится в целых единицах.
- Доступное количество в `products.stock_quantity` уменьшается при создании заказа и увеличивается при отмене.
- В MVP заказ после создания имеет статус `NEW`.

## 4. Функциональные требования
**FR-01 Каталог.** Система должна возвращать активные товары с идентификатором, названием, описанием, ценой и доступным количеством.

**FR-02 Создание заказа.** Система должна принимать одну или несколько позиций с `product_id` и `quantity`.

**FR-03 Валидация.** Система должна отклонять пустой список позиций, неизвестный товар, нецелое или неположительное количество.

**FR-04 Проверка остатка.** Перед созданием заказа система должна проверить достаточность остатка по каждой позиции.

**FR-05 Атомарность.** Если остатка недостаточно хотя бы для одной позиции, система не должна создавать заказ или изменять остатки по любой позиции.

**FR-06 Фиксация цены.** Система должна сохранять цену каждой позиции на момент создания заказа.

**FR-07 Просмотр заказа.** Система должна возвращать заказ, позиции, количество, цену на момент покупки, итоговую сумму и статус.

**FR-08 Отмена заказа.** Система должна разрешать отмену только заказа со статусом `NEW`.

**FR-09 Возврат остатка.** При успешной отмене система должна увеличить остаток каждого товара на количество соответствующей позиции ровно один раз.

**FR-10 Идемпотентность создания.** Система должна поддерживать заголовок `Idempotency-Key`. Повтор с тем же ключом и тем же телом должен возвращать исходный результат без создания второго заказа.

**FR-11 Конфликт ключа.** Если тот же ключ повторно использован с другим телом, система должна вернуть `409 IDEMPOTENCY_KEY_REUSED`.

**FR-12 Структурированные ошибки.** Ошибки API должны содержать стабильный код, понятное сообщение и при необходимости детали поля.

## 5. Нефункциональные требования
**NFR-01 Целостность данных.** Операции создания и отмены заказа должны быть транзакционными.

**NFR-02 Конкурентность.** При параллельных запросах нельзя допустить отрицательный остаток или резервирование одного и того же остатка дважды.

**NFR-03 Безопасность транспорта.** Внешний API должен работать по HTTPS в среде развёртывания.

**NFR-04 Валидация входных данных.** Сервер не должен полагаться исключительно на валидацию на клиенте.

**NFR-05 Наблюдаемость.** Сервер должен логировать идентификатор запроса, операцию, результат и код ошибки, не записывая секреты.

**NFR-06 Документированность.** Контракт API должен быть описан в OpenAPI.

**NFR-07 Производительность (целевое значение для учебного стенда).** При тестовой нагрузке до 50 запросов в секунду 95-й перцентиль ответа чтения каталога должен быть не более 500 мс. Значение является проектным допущением и требует измерения.

## 6. User Stories и критерии приёмки
### US-01 Оформление заказа
Как покупатель, я хочу оформить заказ из доступных товаров, чтобы приобрести нужные позиции.

**AC-01:** Given для всех товаров достаточно остатка, When покупатель отправляет корректный запрос, Then система создаёт заказ со статусом `NEW`, сохраняет цену на момент заказа и уменьшает остатки.

**AC-02:** Given остатка одной позиции недостаточно, When покупатель отправляет запрос, Then система возвращает `409 INSUFFICIENT_STOCK`, заказ не создаётся, остатки не изменяются.

**AC-03:** Given запрос содержит `quantity = 0`, When запрос отправлен, Then система возвращает `400 VALIDATION_ERROR`.

### US-02 Защита от повторного запроса
Как покупатель, я хочу, чтобы повторная отправка запроса из-за сетевого сбоя не создавала второй заказ.

**AC-04:** Given запрос уже обработан, When тот же ключ и то же тело отправлены повторно, Then возвращается первоначальный результат и новый заказ не создаётся.

**AC-05:** Given ключ уже использован с другим телом, When поступает новый запрос с этим ключом, Then возвращается `409 IDEMPOTENCY_KEY_REUSED`.

### US-03 Отмена заказа
Как покупатель, я хочу отменить ещё не отменённый заказ, чтобы вернуть товары в доступный остаток.

**AC-06:** Given заказ имеет статус `NEW`, When покупатель отменяет его, Then статус меняется на `CANCELLED`, а остатки восстанавливаются один раз.

**AC-07:** Given заказ имеет статус `CANCELLED`, When пользователь повторно отменяет его, Then система возвращает `409 ORDER_NOT_CANCELLABLE` и не меняет остатки.

## 7. Вопросы для следующей итерации
- Нужна ли авторизация и как проверяется владелец заказа?
- Нужно ли хранить историю переходов статусов?
- Должен ли заказ поддерживать частичную отмену?
- Как обрабатывать изменение цены между просмотром каталога и оформлением?
- Требуется ли резервирование с TTL и отдельная операция подтверждения оплаты?
